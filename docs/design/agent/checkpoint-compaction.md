# 检查点驱动的状态收敛

> 历史设计说明：本文涉及的固定流水线已移除。当前实现、持久化事件与恢复 API 以[静态图指南](static-agent-graph.md)和[单 Agent API](operator-only-api.md)为准。

状态：设计提案，尚未实现。适用于 Operator pipeline 的内存和持久化宿主。

后续方案：流式输出优先采用 [追加日志与轻量检查点](append-only-output.md)，从写入源头避免完整前缀快照。本文件中的通用归档/裁剪约束仍适用于历史保留和回收，不再作为解决流式重复存储的前置步骤。

## 目标与当前问题

以成功提交的检查点为触发点，将已处理历史移出热状态，使恢复只需加载检查点和其后的增量。这里的压缩是无损状态收敛；不使用模型摘要替代对话，也不改变模型接收到的历史消息。

当前检查点 map 对同一个 key 只保存最新版本，但该版本的内容仍可能持续增长：

- `EffectRun.public_events` 累积对外事件；`stream.rs` 定期加载整个 record 后筛选新事件。
- `EffectOutputState.batches` 累积输出批次；`effect_output.rs` 的 flush 还会写入截至当前的完整 journal。
- `MemoryFabric` 保存事件、回执和死信；事务快照共享检查点的 Arc，但读取检查点仍会复制 value。
- `ScanEvents` 使用数组位置生成 offset；订阅流使用匹配事件的计数生成 offset。删除数组前缀会改变旧游标的含义。
- `public_events` 的新序号存在由 `len() + 1` 生成的路径；裁剪前必须改为显式递增计数。
- `InspectRetention` 目前只盘点，不执行安全回收。

便利流入口为每次 run 创建独立 MemoryFabric，因此其增长主要发生在单次运行中。长期共享 Fabric 和文件 blob 的回收需另行按保留策略管理。当前单个检查点上限为 4 MiB，HTTP 请求体 50 MiB 并不改变此限制。

## 数据形态

将运行数据拆为三类：

1. 热检查点：reducer 当前状态、待处理 effect、审批/等待状态、版本、消费水位、下一条公开事件序号，以及归档索引引用。不要内嵌所有输出批次和公开事件。
2. 不可变历史段：输出 delta、公开事件、完成的批次及大内容。每段携带 run/tenant、首尾序号、内容校验值和格式版本，可按游标分页读取；索引也需分页，避免把无限增长的段列表搬回检查点。
3. 去重和恢复元数据：事件身份及内容指纹、effect 结果引用、回执、租约 epoch、每个消费者的确认位置。其生命周期独立于输出正文。

恢复时加载热检查点，验证引用段存在且校验正确，再重放检查点之后的增量。模型需要的完整历史可通过引用读取，不能因热状态收敛而丢失。

## 提交与收敛流程

每次检查点成功提交后，仅检查增量计数/字节计数；达到阈值才安排收敛，不能在每次 token 或每次查询时扫描全量状态。

1. 取得检查点版本及已覆盖范围，生成不可变历史段；存储必须先确认段可读，持久化宿主还需满足其耐久性契约。
2. 通过版本比较事务提交新检查点、历史段索引引用和对应 outbox/消费位置。版本冲突则重新规划，不能覆盖并发输出。
3. 提交成功后计算可回收范围。只释放已归档、被检查点覆盖、且不再被活跃读取者/待处理操作引用的热正文。
4. 删除旧段属于后续保留策略。先标记、再经过宽限期和引用复查回收；失败可重试。

段写入后事务失败只会留下孤儿段；事务提交前不得删除旧数据。回收中断应只造成多占空间，不应造成恢复缺口。内存宿主也需在同一进程生命周期内保证归档引用有效，不能把数据搬入另一个永不释放的 Vec 就视为内存优化。

## 安全水位与序号

- 先引入存储时分配的稳定全局位置，以及稳定的订阅位置/过滤映射；删除数据后不重新编号。
- 全局位置、订阅 offset、公开事件 seq、模型 delta seq 是不同坐标，不能直接取它们的最小值。应逐事件判断覆盖和消费条件，或显式转换到同一坐标后计算水位。
- 保留未确认消费者需要的数据，包括未派发 outbox、有效租约、重试任务、待审批/等待 effect、死信及其依赖引用。
- SSE 写入 socket 不等于客户端确认。便利流可使用进程内读取游标保护当前读者；支持重连的宿主还必须保留回放窗口或归档读取能力。
- 新订阅必须明确从何处开始。请求的历史超出保留范围时返回明确的游标过期错误，不能静默跳过。
- 公开事件序号使用显式 `next_public_seq`；压缩前后保持身份、顺序及终止事件一致。
- 删除正文后仍需保留去重证据及生产者序号水位；不能让重发旧事件再次触发工具副作用。去重证据的裁剪必须有明确的重试期限或关闭分区契约。

## 输出路径的具体改造

先把 `public_events` 从整个 run checkpoint 的读取路径分离，提供按 `after_seq` 读取页面的接口；流适配器每次只读取新增页面。随后把 `batches` 改为历史段索引引用。

输出 journal 只追加新段，避免每个 flush 重写完整前缀。当前 coverage digest 校验和最终 seal 依赖完整 journal，迁移时需要版本化的增量校验结构，或在 seal 时读取归档段验证原校验语义；不能直接用一个新 hash 替代旧算法而不修改校验契约。

通用 Fabric 只负责事务、稳定位置和存储机制；哪些状态已被 reducer 覆盖由 pipeline 显式声明，不能通过猜测 JSON key 自动删除。

## 触发与观测

建议初始可配置阈值：新增 256 个历史事件或 512 KiB 历史正文时触发，最短间隔 1 秒；这些是待基准验证的起始值。长时间无消费者确认时允许水位不前进，配合积压限制和背压，不能为满足内存目标强删。

归档、编码和可选的字节压缩在锁外执行，同一分区最多一个收敛任务。提交时只做短事务和版本检查。Zstd 等字节压缩可用于冷数据，不宜在高频检查点读取路径反复解压。

记录热状态字节数、归档字节数、已收敛事件数、耗时、版本冲突数、安全水位和阻止回收的原因。不得在这些日志中输出正文、图片或密钥。

## 实施顺序与验收

1. 增加稳定位置和显式公开事件计数，兼容旧快照；保持旧回放行为。
2. 分离公开事件读取和输出历史段，保留完整历史；验证逐页结果与原输出完全一致。
3. 增加版本校验的收敛提交，先启用热正文释放，再启用带保留期的物理回收。
4. 分别接入 MemoryFabric 和 SQLite，确保耐久性、旧快照迁移和保留范围契约一致。

必须覆盖：慢消费者、多订阅不同过滤、租约过期重投、待派发 outbox、审批/工具重试、取消、并发 checkpoint 冲突、重连游标、压缩各阶段故障恢复，以及旧事件重发不会再次执行副作用。

长流基准至少覆盖一万个片段、多次收敛：对比完整输出及序号，测量首片段和后半程延迟、峰值内存、归档写入量。验收重点是热历史不随已归档输出线性增长，归档写入量接近新增数据量；业务必需的 reducer/对话状态仍可能增长，不能承诺整个进程恒定内存。
