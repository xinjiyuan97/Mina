> 历史设计说明：本文涉及的固定流水线已移除。当前实现、持久化事件与恢复 API 以[静态图指南](static-agent-graph.md)和[单 Agent API](operator-only-api.md)为准。

状态：分阶段实施中。下文是目标设计，当前落地范围见本节；优先于通用检查点压缩推进。

### 第一阶段已落地

- Operator 输出 journal 改为不可变增量 chunk，每段引用上一段，只在恢复和 seal 时重建。读取兼容旧的完整数组 journal；新写入的链式格式不支持旧二进制读取，持久化部署需统一升级读取端，不能直接降级。
- 输出聚合器只缓存未提交片段，按时间、片段数或字节阈值 flush，提交后释放。接收顺序必须与模型侧分配的 delta_seq 连续一致，累计容量限制不因释放缓冲而重置。
- 流式 flush 增量维护 SHA256 内存状态，保持原有 `coverage()` 字节编码和结果。这里尚未采用下文的新版持久化哈希链；恢复时仍需读取历史计算摘要。
- MemoryFabric 事务快照通过 Arc 共享事件和回执正文；派发可见性修改使用写时复制，保留回滚隔离和序列化格式。订阅遍历惰性执行，只复制请求返回的事件，不构造完整回放列表。
- 便利流使用 coordinator 提交后的 watch 通知唤醒，保留 250ms 控制补查；RunStore 投影仅追加其已有游标之后的公开事件。

### 第二阶段：输出批次独立存储

新运行的 `EffectOutputState` 不再内嵌历史 `batches`。每个批次按 tenant/run/effect/first_seq 独立保存一次，输出头只维护进度、摘要、journal 引用和 sealed 标记。coordinator 根据批次 key 读取并核对版本、正文和已提交水位，不再扫描不断增长的批次列表。

新增 `GuardedTransactMany`：校验当前未确认租约，把批次记录、输出头和 outbox 在同一事务中提交，但不确认模型调用的 delivery。这样同一调用可以连续 flush；任意记录版本冲突、过期租约或跨 run outbox 均不能部分提交。MemoryFabric 与 SQLite 共用这组转移逻辑。

旧快照中的内嵌批次继续用于校验，不会被自动删除；其后新批次写入独立记录，旧列表停止增长。新快照省略空的 `batches` 字段，读取端以空列表兼容缺省字段。新格式仍要求统一升级读取端，旧二进制不能消费这些独立批次。

第二阶段验证：512 片段输出内容和序号完全一致，输出头不含 `batches` 且序列化小于 512 字节，每批均有版本为 0 的独立记录。6 项事务测试、5 项流式测试、10 项 effect pipeline 测试、2 项进程恢复测试、76 项 Core 单元测试及 3 项 demo 测试通过；本地 HTTP 测试在允许监听端口的环境重跑通过。沿用对既有 `collapsible_if` 告警的单项放行后 Core Clippy 通过，边界检查通过。

### 第三阶段：公开事件追加日志

Operator/tools 路径的公开事件已从 `EffectRun` 拆到 Fabric 日志。每次转移的新增公开事件、checkpoint、回执及 outbox 通过 `TransactLog` 原子提交，以 `public_event_count` 校验追加位置；序号不依赖已加载历史长度。新运行 checkpoint 不再序列化 `public_events`。

`ReadLog` / `read_public_events` 按 after 游标分页，最多 128 条且受 4 MiB 页大小限制；内存路径直接定位数组位置，仅复制本页。便利流、RunStore 投影使用分页读取；调度、控制与引擎恢复使用不含历史的 `load_state`。公开的 `load` API 保持兼容，按捕获的检查点水位重建完整历史，但不用于流式轮询。

旧 inline checkpoint 可直接分页读取，在下一次有效状态更新时将旧历史和本次新事件一同迁移，序号保持不变。迁移与读取交错时会复查日志，避免把迁移中的短暂读取顺序当作数据缺失。日志中的附件引用也纳入 retention 盘点根。

首次写入日志将 Fabric 存储版本升级为 2；新 SQLite 读取器接受版本 1/2，旧二进制会拒绝版本 2，避免忽略日志字段后覆盖数据。升级后不能用旧二进制继续写同一数据库。已有非 Operator/tools 文本 profile 的 `PipelineRecord` / projector 暂未迁移。

第三阶段验证：分页拼接与完整事件历史一致，原始运行 checkpoint 不含公开事件列表；旧 inline 历史迁移保持序号。Core 全套测试（含 77 项单元测试）、33 项 Fabric 契约测试、8 项事务测试、流式/审批/工具/等待/进程恢复测试及 demo 逐段 HTTP 测试通过。沿用单项放行既有 `collapsible_if` 告警后 Core Clippy 通过，边界检查通过。

默认内存路径已移除模型侧重复 journal，并在结束时直接转交 journal 所有权。尚未落地：durable 兼容路径的模型侧完整 journal 移除、Fabric 投递索引、事务全量容器复制消除及历史 GC。reducer 必需的对话状态和模型终结核对仍随内容增长；SQLite 已按记录增量写入，公开日志使用数据库分页查询，详见 [SQLite 增量存储](sqlite-incremental-storage.md)；协调事件与回执仍需在事务中加载。不能据此宣称全链路恒定内存或全部写入均为 O(N)。输出 journal 的按序号分页索引仍需另行实现。

当前不执行 blob 回收。未来启用 GC 时必须从存活 head 沿 `previous` 遍历依赖，保护整条链；现有 `InspectRetention` 不解析 blob 内部引用，其孤儿候选不能直接作为删除这些链节点的依据。

本阶段验证：Core、Harness、Extension 测试通过，覆盖事务回滚、SQLite 重开、进程退出恢复、工具去重和流式 seal；新增 chunk/旧数组兼容、缺口/重叠拒绝、增量摘要一致性、共享快照隔离及分页测试。demo 的 96 段逐段 HTTP 输出测试通过。严格 Clippy 仍有既有 `engine.rs:190` 的 `collapsible_if` 告警；仅放行该规则后检查通过。尚未完成一万个片段的全链路内存和吞吐基准。

## 决策

流式输出一旦发布便不可修改，因此保存新增内容和稳定位置即可，不必保存输出的每个完整前缀。检查点保存继续执行所需的当前状态，日志保存已经发生的事实，两者通过水位关联。

当前 Fabric 对相同 checkpoint key 已经只保存最新版本，问题不是保留了所有旧版本，而是最新版本包含不断增长的历史，并且 flush 会产生完整 journal 前缀的新 blob。优化目标是消除这种重复写入和读取。

例如依次收到“你”“好”“！”：

```text
追加日志： [1, “你”] [2, “好”] [3, “！”]
输出头：   committed_through = 3
检查点：   applied_through = 3，当前执行状态
读取者：   after_seq = 2 → 只读取 [3, “！”]
```

不再生成“你”“你好”“你好！”三个前缀文件。完整回答在需要时按顺序拼接，可以在结束时生成一次最终消息供多轮上下文使用。

## 范围与身份

追加规则适用于已接收、已发布的输出事实。reducer、审批、工具状态仍会更新，不能把整个 Agent 状态视为只追加字符串。

- 输出流身份为 `(tenant, run_id, effect_id, invocation_id)`；一次新模型调用不能复用已中断调用的身份。
- `delta_seq` 在调用内递增，保留原始通道和 block/tool-call 标识，区分正文、推理、工具参数及控制事件。
- `public_seq` 在 run 内递增，统一排列公开的输出、审批、用量及终止事件。
- Fabric 投递位置与以上序号不同，不能互换或按数组长度推导。
- 公开后需要更正内容时产生显式的新事件或新消息，不能覆写旧日志；若以后协议支持编辑，需要另行定义编辑语义。

## 最小数据模型

| 数据 | 保存内容 | 增长方式 |
| --- | --- | --- |
| OutputChunk | 不可变的新 delta 范围、通道、内容、校验值 | 只写新段 |
| OutputHead | 流身份、版本、已提交 seq、累计字节、增量摘要、sealed 状态 | 固定字段更新 |
| PublicEventLog | public_seq、事件类型、输出段引用或小型控制内容、稳定去重键 | 只追加新事件 |
| RunCheckpoint | reducer 状态、待执行任务、各输入水位、已应用输出水位 | 更新当前状态 |
| OutputFinal | 最终 seq、摘要、用量、结束原因 | 每个调用结束提交一次 |

输出正文以 OutputChunk 为唯一日志正文来源。公开事件和 outbox 引用 chunk 及其范围，不重复内嵌全部文本；公开事件读取时解析所需引用。工具执行结果等独立事实保持自己的数据契约。

chunk 索引按流和序号分页查找，不能把全部 chunk 引用放回检查点。输出头字段固定，但整个运行检查点仍会随业务必需的对话/任务状态增长，不承诺全局恒定内存。

## 写入流程与事务

模型读取端维护有界待提交缓冲，达到现有 40 ms 窗口、128 个片段或 32 KiB 阈值之一时提交新增段；最后不足一批的内容在结束前 flush。单条超大 delta 必须明确拒绝或按协议允许的方式拆分，不得绕过字节上限。

建议新增专用存储操作，以下为接口草案：

```text
AppendOutput(identity, lease_epoch, expected_head, append_id, new_chunk)
ReadOutput(identity, after_seq, max_items, max_bytes)
ReadPublicEvents(tenant, run_id, after_seq, max_items, max_bytes)
SealOutput(identity, expected_head, final_metadata)
```

`AppendOutput` 在同一事务中校验租约和 head 版本、插入 chunk 索引、推进 head、写入引用型 `output.batch` outbox。成功后才通知消费者，生产端才能释放该批缓冲。模型输出量上限继续依据累计计数执行，不能因释放缓冲而重置。

正文可在事务前写入不可变 blob，但只有事务提交后的引用才可见；失败留下的孤儿 blob 延后回收。MemoryFabric 采用专用小范围变更或结构共享，不通过复制所有历史来实现该事务；持久化宿主使用数据库原子事务。无法提供这一原子性时不能启用该写入路径。

coordinator 消费已提交段，校验引用及连续性，应用 reducer 转移，并在一个事务中更新 RunCheckpoint、追加新的 PublicEventLog 索引、提交投递回执和后续 outbox。这样崩溃重试不会重复产生公开事件或工具调度。

这里只将输出从 checkpoint 中分离；如果 reducer 本身仍复制累计文本，仍需让其输出累积使用引用/可增量更新的投影。逐项测量该开销，不能仅删除 `public_events` 就宣称消除了全部累积成本。

## 顺序、去重和摘要

- 每个流使用一个受租约 epoch 保护的写入者；多个写入者竞争时通过版本比较失败重试，旧 epoch 不得提交。
- 下一批必须从 `committed_through + 1` 开始；发现缺口不推进水位。
- 同一 `append_id` 重试时验证流身份、范围和内容指纹，完全一致则返回原结果，不重复追加。相同身份内容不同返回冲突。
- 首版不支持用不同批次边界重提交已提交的重叠范围；恢复后先查询 head，仅读取或追加剩余部分。未确认批次重试保持原 append_id 和边界。
- public event 使用来源事件/输出段加事件序号组成稳定去重键；`public_seq` 由事务分配，不能使用内存数组长度。
- 引入版本化逐 delta 哈希链：`H_i = SHA256(domain || H_(i-1) || length(canonical_delta_i) || canonical_delta_i)`。初始值绑定流身份和格式版本，编码固定；它不依赖批次边界，可以从 head 继续计算。
- 当前 `coverage()` 是整个 journal 的 SHA256，不能直接当成上述链的状态。新旧摘要明确区分；旧运行沿用旧算法，新运行使用新格式。

## 流式读取

SSE 读取者保存自己的 public_seq，仅查询其后的页面，组装协议事件后发送。取消和审批继续通过独立控制路径处理，不要求加载全部输出。

通知仅用于唤醒，存储才是事实来源。采用“注册通知后再查日志”的顺序，或可感知版本变化的通知机制，并保留低频补查，避免查询与等待之间丢通知。慢客户端使用分页与背压，不能给每个客户端维护无界消息队列。

服务端写出 SSE 不代表客户端已确认；重连时以协议游标读取已提交事件。保留期外的游标返回明确错误。当前 demo 未实现重连回放，增加日志不等于自动增加该协议能力。

## 结束与故障恢复

正常结束先等待最后一批持久化，再提交 OutputFinal 和 seal，coordinator 完成其前面的输出投影后才发布终止事件。sealed 后拒绝新增正文，重复 seal 仅在内容相同时成功。

| 中断位置 | 恢复行为 |
| --- | --- |
| chunk 正文已写、事务未提交 | 正文不可见，旧 head 有效；重试提交或回收孤儿 |
| append 已提交、调用方未收到确认 | 使用相同 append_id 重试，返回原提交结果 |
| 输出已提交、coordinator 尚未消费 | 从 applied_through 后继续消费 |
| checkpoint/公开事件事务提交后崩溃 | 回执和去重键阻止重复投影及副作用调度 |
| SSE 中断 | 按有效 public_seq 回放，客户端按事件身份去重 |
| 模型连接丢失或进程退出 | 保留已提交前缀，将该 invocation 标记中断；不能假装模型可以从 token 位置续传 |

除非模型服务明确支持可靠恢复，否则重新生成属于新 invocation，应通过新的公开事件表达。未提交缓冲可能在进程崩溃时丢失，因此 durable 模式仅发布已提交段。内存模式只保证进程内一致性，不承诺重启恢复。

最终校验使用 head 的 seq 和摘要，不再读取完整 journal 来构造 ModelFinal。若有独立生产端摘要需核对，则生产端增量维护该摘要并在 drain 完成后比对。需要重新构建完整内容时按段读取；故障修复只补充具有独立可靠来源的缺口，不能推测丢失文本。

## 对当前代码的改造

1. 增加输出/公开事件日志存储契约及事务能力，先完成内存和持久化实现的顺序、去重和恢复测试。
2. `EffectOutputState` 删除 `batches` 和完整前缀 `journal_ref`，使用 OutputHead；`effect_output.rs` 只 flush 新增缓冲，提交后释放。
3. `effect_model.rs` 删除全量 journal 累积，显式维护 next_seq、字节数和增量摘要；`ModelFinal` 改为元数据及日志引用。保持输出限额和 drain 顺序。
4. `effect_coordinator.rs` 通过已提交 chunk 索引验证批次，替换 `output.batches.contains()`；公开事件追加与 checkpoint 更新原子提交。
5. `EffectRun` 移除 `public_events`，`stream.rs` 改为按游标读取；文本 profile 的 `projector.rs` 也改为只投影新增段，避免继续从所有 batch 重建公开历史。
6. 新运行使用新格式；已有运行在原格式下完成，或经显式迁移工具一次性转换并核验。禁止读写途中混用摘要和序号规则。

首阶段不删除 Fabric 旧事件，不实施通用 GC。日志本身仍需要 O(N) 存储；先消除 O(N²) 的完整前缀写入。后续再按保留期清理整个终结运行，或按明确水位归档历史段。

## 验收

- 正文、推理、工具参数交错输出的内容和顺序与旧实现一致；终止事件只出现一次且在所有正文之后。
- 批次重复、冲突、缺口、旧租约、并发提交及上述故障点均有契约测试。
- 慢客户端、有界缓冲和通知丢失场景下不漏事件、不无限堆积内存。
- 一万个片段的长流测试统计实际写入字节和 checkpoint 大小：日志写入量随新增内容线性增长，输出头不随片段数增长，读取只返回 cursor 后的数据。
- 对比前后半程流式延迟及峰值内存；输出层常驻正文受缓冲和缓存预算约束。完整对话上下文、reducer 必需状态和无磁盘的 MemoryFabric 历史单独计量，不能用这些例外掩盖重复前缀存储。
